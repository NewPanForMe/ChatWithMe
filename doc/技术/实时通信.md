# 实时通信

> 客户端实时性由 **SignalR（WebSocket）** 提供。它负责“服务端把消息推到在线客户端”，不承担服务端解耦、削峰或离线队列。

## 1. 为什么不是 RabbitMQ

- RabbitMQ 是服务端消息队列，解决服务间解耦、削峰、多消费者；它**不会**把消息推到客户端。
- 本项目后端已用 SignalR Hub 向会话组广播；客户端连上 Hub 即实时。
- 单实例部署用进程内推送已足够；**多实例**时才需要给 SignalR 加 **Redis backplane**（也不是 RabbitMQ）。

## 2. Hub

- 路径：`/hubs/chat`，`[Authorize]`，使用聊天用户令牌（`typ=user`）。
- 连接生命周期：
  - `OnConnectedAsync`：把用户登记到在线表（多端登录计多条连接）。
  - `OnDisconnectedAsync`：移除连接；连接数为 0 时下线。
- 方法：
  - `JoinConversation(conversationId)`：校验成员后加入组 `conversation:{id}`；非成员抛 `HubException`。
  - `LeaveConversation(conversationId)`：退出组。
- 客户端连接时用 `AccessTokenProvider` 提供当前 access token；令牌过期后重连会取最新值。

## 3. 事件

| 事件 | 触发 | 接收方 | 载荷 |
| --- | --- | --- | --- |
| `messageReceived` | 消息成功落库后（幂等命中不重复广播） | 该会话组成员 | `MessageDto` |
| `notificationReceived` | 管理员发送全员通知并保存成功后 | 聊天用户连接（不含管理端连接） | 通知 DTO |

广播抽象：`Application.Realtime.IChatNotifier` / 通知广播服务；Api 层用 `IHubContext<ChatHub>` 实现，Application 不直接依赖 SignalR。

## 4. 在线状态与踢人

- 在线登记表为进程内实现（`IOnlineUserRegistry`），记录 `userId → connectionIds`。
- `GET /api/admin/users/online` 返回在线用户与连接数。
- `POST /api/admin/users/{id}/kick` 会 `Abort()` 该用户所有连接（同时自增会话版本、吊销 refresh token，见 [账号与权限](../账号/账号与权限.md)）。
- 多实例部署时在线表与踢人都需要共享存储（Redis），当前实现是单实例假设。

## 5. 客户端行为

桌面端（Avalonia）：

- `ChatConnection` 使用 `Microsoft.AspNetCore.SignalR.Client`，`WithAutomaticReconnect()`。
- 登录后连接 Hub，并把当前所有会话逐一 `JoinConversation`；打开/新建会话时补加入；重连后重新入组。
- 收到 `messageReceived`：在 UI 线程按消息 Id 去重后追加到当前会话，并自动滚到底部。
- 收到 `notificationReceived`：弹标题为「通知」的浮动提示，侧栏「通知」页可查历史；推送与补拉按 Id 去重。
- 时间：SignalR 推送默认是 ISO-8601，客户端统一转成本地 `yyyy/MM/dd HH:mm:ss`；HTTP 接口本身输出配置时区格式。

## 6. 断线与降级

- 客户端 `WithAutomaticReconnect()` 自动重试；重连成功触发重新入组与通知补拉。
- HTTP 请求遇 401 时客户端用 HttpOnly Cookie 刷新一次 access token 后重试；刷新失败则清理会话回到登录页。
- 实时连接失败不影响 REST：仍可手动刷新会话/消息，状态栏会提示“实时连接失败（消息仍需手动刷新）”。

## 7. 测试现状

- 后端有 SignalR 相关的单元/集成测试（在线登记、踢人、通知广播）；桌面端有连接与去重测试。
- 本地做过真实 HTTP/WebSocket 两客户端广播与权限验证；桌面界面手工联调尚未覆盖全部场景。
