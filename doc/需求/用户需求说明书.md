## 2. 文档目的与范围

**目的**：明确聊天软件的目标用户、核心业务目标、用户场景与可验收的用户需求，作为产品设计、开发排期与测试验收的共同依据。

**范围内（首版 MVP）**：

- 账号注册登录、多端在线
- 好友添加与联系人管理
- 单聊文本消息、图片/文件消息
- 群聊创建与群消息
- 消息实时送达、离线拉取、已读回执、撤回
- 在线状态与断线重连
- 基础管理后台

**范围外（本期不做）**：

- 音视频通话
- 端到端加密
- 历史消息全文搜索（列入后续版本）
- 跨地域多活集群
- 复杂内容审核与合规审计（仅保留基础敏感词拦截）

## 3. 业务目标与成功指标

| 编号 | 业务目标 | 成功指标（可度量） |
| :--- | :--- | :--- |
| G1 | 用户能稳定地实时聊天 | 在线消息端到端 P99 延迟 < 500ms |
| G2 | 消息不丢、不重、不乱序 | 消息丢失率 = 0；重复消息率 = 0；单会话内有序 |
| G3 | 弱网/断线后能恢复 | 断线重连成功率 ≥ 99%；重连后 10s 内补齐消息 |
| G4 | 多端体验一致 | 同一账号多端在线时，消息在 3s 内同步到各端 |
| G5 | 基础治理可用 | 管理员可在 1 分钟内完成封禁/解散群操作 |

## 5. 用户需求（按模块）

> 优先级采用 MoSCoW：**M**=必须有，**S**=应该有，**C**=可以有，**W**=本期不做。

### 5.1 账号与登录

| 编号 | 用户需求（用户故事） | 优先级 | 用户可验收标准 |
| :--- | :--- | :--- | :--- |
| U-A1 | 作为新用户，我希望用手机号/邮箱注册并登录，以便开始聊天 | M | 注册成功后可登录；密码强度不足时有明确提示；连续输错有锁定/限流提示 |
| U-A2 | 作为用户，我希望在多个设备上同时在线，以便手机和电脑都能收消息 | M | 同一账号两端登录后，任一端发送的消息，另一端在 3s 内可见 |
| U-A3 | 作为用户，我希望登录状态能安全保持，不用频繁重输密码 | M | 短期凭证过期后自动刷新；刷新失败才要求重新登录 |
| U-A4 | 作为用户，我希望可以主动登出，或在异常时被强制下线 | M | 登出后立即无法收发；被踢下线时给出明确提示 |

### 5.2 好友与联系人

| 编号 | 用户需求（用户故事） | 优先级 | 用户可验收标准 |
| :--- | :--- | :--- | :--- |
| U-B1 | 作为用户，我希望搜索并添加好友，以便建立会话 | M | 可搜索到其他用户；不能添加自己；重复申请有提示 |
| U-B2 | 作为用户，我希望处理好友申请，以便决定是否建立关系 | M | 同意后双方好友列表同步出现对方；拒绝后申请关闭 |
| U-B3 | 作为用户，我希望管理好友备注、删除好友、拉黑 | M | 删除后会话保留但不能再发消息；拉黑后对方无法发消息和申请 |
| U-B4 | 作为用户，我希望看到好友的在线状态 | S | 好友在线/离线状态可见；多端在线时显示为在线 |

### 5.3 单聊

| 编号 | 用户需求（用户故事） | 优先级 | 用户可验收标准 |
| :--- | :--- | :--- | :--- |
| U-C1 | 作为用户，我希望发送文本消息并立即看到发送状态 | M | 消息显示“发送中→已送达→已读/失败”；失败可重试且不产生重复消息 |
| U-C2 | 作为用户，我希望对方离线时消息不丢失，上线后能收到 | M | 接收方离线期间的消息，上线后按时间顺序补齐；不重复、不乱序 |
| U-C3 | 作为用户，我希望知道对方是否已读 | S | 对方阅读后，发送方看到“已读”标记 |
| U-C4 | 作为用户，我希望发错消息可以撤回 | S | 发送后 2 分钟内可撤回；双方界面同步移除该消息 |
| U-C5 | 作为用户，我希望发送图片和文件 | S | 图片可预览；文件可下载；大文件有大小限制提示 |

## 6. 用户可感知的非功能需求

| 维度 | 用户需求描述 | 验收口径 |
| :--- | :--- | :--- |
| **实时性** | 在线聊天要“像面对面一样快” | 在线消息 P99 端到端 < 500ms |
| **可靠性** | 消息不能丢、不能重、不能乱 | 消息丢失率 0；重复率 0；单会话有序 |
| **恢复能力** | 断网/切后台回来后，消息要自动补齐 | 重连成功率 ≥ 99%；10s 内补齐 |
| **多端一致** | 手机和电脑看到的消息一致 | 多端同步延迟 ≤ 3s |
| **安全与隐私** | 聊天内容传输加密；未授权的人看不到会话 | 全链路 WSS/HTTPS；越权拉取被拒绝 |
| **易用性** | 发送失败有明确提示和重试入口 | 失败状态可见；一键重试；不产生重复 |
| **可用性** | 核心聊天功能持续可用 | 核心链路可用性 ≥ 99.9% |

## 7. 假设与约束

1. **假设**：用户设备具备基本网络能力；首版以移动端和 Web 端为主。
2. **约束**：首版不承诺端到端加密；消息默认保留 180 天，超期归档或删除。
3. **约束**：群成员上限、单文件大小、消息长度等需在详细设计中给出可配置上限。
4. **依赖**：离线推送依赖第三方推送通道（APNs/FCM/厂商通道），其可达性不在本系统完全控制范围内。

---

## 8. 验收红线（业务方最关心的五条）

1. **消息不丢**：服务端确认落库后才算发送成功；接收方上线必须能拉到。
2. **消息不重**：弱网重试、多端重发不得产生重复消息。
3. **单会话有序**：同一会话内消息按服务端时间有序展示。
4. **重连可恢复**：断线重连后自动补齐消息，且不引发重连风暴。
5. **权限不越界**：拉历史、进群、搜索都必须校验成员身份，不能只靠前端隐藏。

## 10. 待确认问题

1. 群邀请是否需要被邀请人确认？首版建议“直接入群”，需业务方确认。
2. 消息撤回时限是否固定 2 分钟？是否需要按消息类型区分？
3. 离线推送是否首版必须？若必须，需明确接入哪些通道。
4. 消息保留 180 天是否符合合规要求？是否需要用户可导出？
5. 管理后台的封禁/解散是否需要二级审批？
